# 作業指示書：作業記録と検証資料の整理

作成日：2026-11-20

## 1. 目的と作業範囲

リリースに向け、次の2点を実施する。

1. 作業記録を履歴フォルダーへ集約し、日付と連番で探せるようにする。
2. 検証資料を整理し、現行の実行手順と過去の結果・変更経緯を分離する。

この文書は実施指示であり、整理完了の報告ではない。アプリの動作変更、ソース構造の変更、テスト素材・ビルド出力の削減は対象外。commit・push・リリースは別途依頼がある場合に行う。

## 3. 作業記録の命名と配置

### 共通ルール

- 作業記録・旧仕様・旧計画・完了済み指示書は`docs/history/`に集約する。
- ファイル名は`YYYY-MM-DD_NNN_内容.md`に統一する。JSONの記録も同じ命名規則で拡張子を維持する。
- `NNN`は日付ごとの3桁連番。時刻表記や`undated`表記を混ぜない。
- 連番は内容から確認できる前後関係を優先した資料の整理順。実際の作成時刻や厳密な実施順を保証する番号とはしない。
- 要件→計画→指示→調査・実装→検証→引き継ぎを、本文にある実際の依存関係に従って並べる。独立した変更は関連資料の近くに置く。
- 日付は文書が主に扱う作業・策定の日を使う。複数日に追記された文書は分割を必須とせず、起点の日付で置き、各追記の日付は本文に残す。
- 名前に含まれる末尾の日付は先頭へ移し、重複させない。内容部分の既存の識別名は原則維持する。
- ファイルの更新日時や一括取り込みコミットの日時を、実際の作業日時として採用しない。
- 今後の新規記録も同じ規則で、その日の末尾へ追加する。通常の追加・追記で既存番号を振り直さない。
- 「ユーザーの作業時期の記憶と本文から補完」という説明は記載しない。以下の合意済み日付を整理用日付として採用する。

## 4. 検証資料の整理

### VERIFICATION.mdに残すもの

- 現行の実行条件・準備・実行コマンド・再利用条件。
- 合格判定、証跡形式、タイムアウト、プロセス分離、失敗時の扱い。
- 自動試験・手動試験・診断計測・対象外の区別。
- ランナー変更時の保守用検証手順。
- 主な検証範囲の簡潔な案内と、詳細記録へのリンク。

実装・スクリプトを読み、手順が現在の引数・動作と合うことを確認する。例として、起動計測の「停止後2回」と後半の「停止後4回」の重複・不一致を解消する。

スイート名・件数・対象区分の基準は`scripts/verification-suites.json`とランナーとする。55→56→57という過去の増加過程や各ケース数を現行手順へ重複掲載しない。カタログにない計算系試験もランナーを確認して説明する。今回の資料整理のためにカタログ・テストコード・ランナーの動作を変更しない。

### 過去結果・変更経緯の保存

- 特定日の合格件数、性能比較、「今回の変更では～」という当時限りの作業範囲、旧期待値の変更経緯は現行手順から分離する。
- 同じ情報を持つ既存の履歴資料があれば、そこへ集約して参照する。固有の情報は削除せず適切な記録へ移す。
- 移す先がない場合は、2026-11-20の連番付き「検証手順から分離した過去記録」を作る。その日付は整理日であり、各試験の実施日は元の記述を維持する。
- 過去の合格を現在のHEADの合格として扱わない。試験の対象・環境・未確認事項・失敗と再試験の区別を残す。

### 2026-11-11_016_TEST_SUMMARY-preview.10.json

`docs/history/records/2026-11-11_016_TEST_SUMMARY-preview.10.json`は2026-11-11、0.1.0-preview.10の記録。`docs/history/2026-11-11_NNN_TEST_SUMMARY-preview.10.json`へ移動する。

JSONの結果・日付・件数などは書き換えず、履歴索引から版と記録日が分かる形でリンクする。既存の参照も更新する。

## 5. 索引と参照の更新

- `docs/history/README.md`に命名規則、連番の意味、日付順の記録一覧を記載する。
- 記録一覧は日付・番号・タイトル・短い位置付けを基本とし、移動対象を漏れなく辿れるようにする。
- `docs/README.md`の「現在の調査記録」を更新し、過去の引き継ぎだけを現在地として案内し続けない。現行資料、履歴索引、版別確認記録への導線を明確にする。
- README、現行資料、履歴同士のリンク、コード・スクリプトからの資料参照をリポジトリ全体で検索する。
- 移動する文書の発信リンクも、その新しい場所を基準に修正する。例えば`docs/`から`docs/history/`へ移す場合、現行資料や画像への相対パスは1階層変わる。
- 通常のMarkdownリンクだけでなく、参照形式リンク、画像、コードブロックやインラインコード中の「資料を開くためのパス」も確認する。
- 過去の実行ログ、証跡の保存パス、旧コミット・旧ブランチ・旧EXE名は記録そのものなので、現在の名前へ機械的に置換しない。
- 外部公開済みタグを指す固定URLは、タグ側に実在する元のパスを維持する。現在のブランチの移動先へ一括置換しない。
- `DISTRIBUTION_README.md`の相対リンクは配布後のアプリ直下を基準としている。リポジトリ内の置き場所だけを理由に変更しない。

## 6. 確認と完了条件

1. 対象全件に移動先があり、名前の衝突・欠番の意図しない発生・ファイルの欠落がない。
2. 履歴索引以外の作業記録は日付＋3桁連番で揃い、時刻形式・undatedが混在しない。
3. 元の記録本文は、参照修正・必要な見出し整理・検証記述の移設以外で変更されていない。
4. ローカルMarkdownリンクと画像パスを点検し、新規リンク切れがない。元から存在した問題は別に報告し、この整理で生じた問題と区別する。
5. 旧パスを検索し、残った参照が歴史的記述・固定タグURLなど意図したものだけになっている。
6. 配布スクリプトの明示リストが参照する資料・画像が存在し、`docs/releases/<Version>.md`の名前が維持されている。
7. JSONが読み込め、`TEST_SUMMARY`の内容が移動前と一致する。
8. `git diff --check`を通し、差分とGit状態を確認する。

資料整理のみのため、アプリの全自動検証や実機試験は不要。アプリを起動したり、既存の配布物・検証証跡を作り直したりする必要もない。

最終報告には移動・改名件数、主な配置、検証資料の整理内容、確認結果、残った参照上の問題があればその内容を記載する。移動対応表は履歴索引または完了記録から確認できるようにする。
