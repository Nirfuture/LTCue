# 現行仕様と技術解説6件の照合

確認日：2026-11-20。現在の作業ツリーにあるFINAL_SPEC.mdとreferenceの6件を比較した。これは構成変更前のレビュー結果であり、移動・改名・統合の完了記録ではない。本書と履歴索引だけを追加・更新し、対象7資料とアプリコードは変更していない。

## 結論

FINAL_SPEC.mdは利用者から見た仕様だけではなく、内部設計・資源上限・採用境界も含む。したがって「現行仕様は外部動作、referenceは内部設計」という説明は現状には当てはまらない。一方、referenceには現行仕様にない契約・制約があり、全文を削除したり、全文を現行仕様へ移したりするのも適切ではない。

先に情報ごとの記載先を決め、重複した説明を参照へ置き換えるべきである。「現行仕様＋補足資料」という関係は、素材障害とHAP準備については既にFINAL_SPEC.mdの明示リンクとして存在する。全資料を新たに「詳細仕様」または「内部設計」へ改称する根拠はまだない。

## 比較の見方

- 重複：同じ動作・条件が既に現行仕様にある。細部の追加まで不要という意味ではない。
- 補足：現行仕様には概略があり、referenceに保守判断に必要な条件・手順がある。
- 未記載：現行仕様には明示されていない。直ちに現行仕様へ追加すべきとは限らない。
- 分類は本レビューの編集上の判断。動作の変更提案ではない。

### 要修正：表示と復旧の混同

SYNC_RECOVERY.mdの「200msまたは3フレームを超えると遅延秒数を画面に表示」は、そのままでは現在の表示仕様として不適切。

- FINAL_SPEC §2とMainWindow.TimingStatusは、映像表示の許容幅をmax(50ms, 1.5フレーム)、継続判定を0.3秒としている。
- ProgramPlaybackはmax(200ms, 3フレーム)を追従復旧の開始判定に使い、診断Warningを生成する。
- MainWindow.Deliveryはプレビューの通知にNoticeを使い、診断Warningをそのまま表示しない。復旧中のタイミング表示には「再同期中」がある。

閾値自体が矛盾しているわけではなく、別の判定を一つの表示説明として書いていることが問題。次回編集では「復旧開始条件」と「画面の同期状態表示」を分ける。先の技術解説整理でもこの点を見落としていた。

確認先：[ProgramPlayback.cs](../../../src/LtcPlayer.Avalonia/Playback/ProgramPlayback.cs)・[MainWindow.TimingStatus.cs](../../../src/LtcPlayer.Avalonia/MainWindow.TimingStatus.cs)・[PlaybackTimingStatus.cs](../../../src/LtcPlayer.Avalonia/Playback/PlaybackTimingStatus.cs)・[MainWindow.Delivery.cs](../../../src/LtcPlayer.Avalonia/MainWindow.Delivery.cs)

現行仕様と補足資料の境界は、利用者/開発者という読者の区分だけでは決まらない。現行仕様には動作・制約の基準、補足にはその基準を守るための具体的な責務・寿命・採用条件を置く。ただし既存資料の全段落が一方に属するとはせず、上表の単位で整理する。
