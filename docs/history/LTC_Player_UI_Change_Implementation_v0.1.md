# LTC Player 操作UI変更 実装手順書 v0.1

作成日: 2026-11-09 JST

対応仕様: LTC_Player_UI_Change_Spec_v0.1.md

対象: outputs/LtcPlayer配下のAvalonia版。これは今後の変更作業の手順書であり、記載した実装・試験は文書作成時点では未実施。

## 1. 作業範囲と開始時確認

1. 本仕様、PHASE5_REPORT.md、README_PHASE5.md、最新のSTART_HERE.mdを読む。
2. 現行のsrc/LtcPlayer.Avalonia、native/phase5、設定、packages.lock.json、最終バイナリのハッシュを保存する。ユーザーが編集した上演JSONや設定を上書きしない。
3. 新しい作業・結果フォルダーを作成する。例: verification/ui-update-YYYYMMDD-HHMMSS/。修正前ビルドも識別可能な状態で残す。
4. SDK 8.0.301、Avalonia 11.3.21、DataGrid 11.3.13、MSVC x64、FFmpegの現行構成を確認する。本変更でSDK/GUIライブラリ更新を混在させない。
5. 旧WPFソースとbin-phase4-final、既存のPhase 5結果は保全する。

コード変更の主対象はsrc/LtcPlayer.Avaloniaとnative/phase5。src/LtcPlayer.AppからリンクしているMediaDecoder、CueProgram、MasterClock、AudioInputService等は極力維持する。共有ソースを変更する必要が生じた場合は、旧WPFへの影響を明記する。

## 2. 現状の変更箇所

| 現行ファイル/処理 | 変更理由 |
|---|---|
| MainWindow.axaml/.cs | 見出し削除、単一表示領域、行操作、設定モーダル、ボタン/状態表示 |
| UpdatePreview | IsPointerOver/IsKeyboardFocusWithinによる追従停止を廃止し、実操作中だけ更新を抑止 |
| RunProductionAsync | 配信ごとに起動しているAudioInputServiceを常時監視サービスへ移す |
| ArmAsync/DisarmAsync/Closing/Esc | 開始/停止/確認/準備中取消を共通の状態管理へ集約 |
| PreviewPlayer | 個別再生のまま維持し、表示権限と遅延通知を制御する |
| PreviewHost | Cue用の表示先に固定された所有関係を、1つの表示領域の貸出しへ整理 |
| Playback/ProgramPlayback | 本番で採用・提示したフレームとモニターを対応させる |
| VideoRenderer/ネイティブ描画 | 本番GPU画像を同一デバイスで縮小表示する入口を追加 |
| native/phase5/Player.cpp等のEsc/WM_CLOSE | 現行の即時DestroyWindowをユーザー停止要求の通知へ変更 |
| Phase5Verification/verify-phase5.ps1 | UI差分の追加試験と、従来のARM表現/受信寿命の期待値変更 |

UIイベントにデコード、キュー選択、LTC時刻計算を追加しない。新サービス名は以下を目安とし、同等の責務分離ができれば名称自体は変更可能。

## 3. 実装順序

### Step 1 — 状態管理と表示の所有権

- 配信状態をStopped / Starting / Streaming / ConfirmingStop / Stoppingへ整理する。異常情報は別に保持し、異常後は停止状態へ戻せるようにする。
- PreviewSurfaceCoordinator等を設け、単一映像領域の所有者をCue / Program / Noneで管理する。
- 世代番号またはセッションIDを発行し、前モードの描画/ステータス通知を破棄する。選択行のロード完了が配信表示を書き換える競合も防ぐ。
- 状態遷移は直列化する。ただし、開始待ちの直列化によってキャンセル要求まで待たせない。
- PreviewPlayerの配信中拒否を維持する。UIの無効化だけに依存しない。

完了確認: 状態遷移、二重開始、停止連打、準備中取消、古いロード結果の拒否を描画機器に依存しない試験で確認する。

### Step 2 — LTC監視をアプリ寿命へ分離

- LtcMonitorService等が選択入力・MasterClock・受信タスク・再接続処理を所有する。
- MainWindow初期化後に開始し、アプリ終了で停止する。RunProductionAsyncから入力の作成/解放を取り除く。
- 配信は監視中のClockを借りるだけとし、配信終了のCancellationTokenで受信タスクをキャンセルしない。
- LTC表示はProgramObservationの有無に依存させず、監視スナップショットで更新する。配信フレーム情報は引き続き本番観測から取得する。
- 設定変更・JSONのLTCモード変更は監視サービスの再構成入口へ集約する。旧タスクの終了を待ち、新しいClock/WAITINGへ切り替える。
- ログは監視イベントと本番イベントの関連をセッションIDで記録する。生音声波形は本作業で保存しない。常時監視ログは無制限に増やさず、必要なセッション/エラー/診断記録へ限定する。
- 試験用LTC供給は監視サービスに注入できる構造とし、通常UIからは合成信号を有効にしない。

完了確認: 配信の繰返し開始/停止で入力のopen回数が増えないこと、停止中の受信、再接続、設定変更時に旧通知が混入しないことを確認する。

### Step 3 — 本番GPUモニターの最小検証

画面全体を変更する前に、次を小さく検証する。

1. 本番で最終的に使ったBGRAテクスチャ（H.264のupload / HAPのrendered）からUI子HWNDへ縮小描画する。
2. 同一D3D11デバイス内でモニター用スワップチェーンを使用し、追加の復号・全画素CPU読戻しを通常経路に入れない。
3. 本番Presentが成功したフレームだけをモニターの更新対象にする。選択キューの先読みフレームを直接表示しない。
4. 更新上限15fps、最大640×360相当、最新1フレームを上限にする。本番PresentをモニターのVSyncやGPU読戻し待ちで止めない。
5. WAITING/黒区間、フレーム保持、H.264/HAP/HAP Q切替、サイズ変更を試す。

UIのNativeControlHostは子HWNDの寿命を所有し、Cue描画と本番モニターはその描画先を借りる設計を推奨する。借用HWNDを本番RendererのDisposeが破棄しないこと。D3Dコンテキストを複数スレッドから同時に操作せず、現行のUIディスパッチ境界との整合性を確認する。

本番用とCue用のリソースを解放してから所有権を渡す。ウィンドウ破棄中に遅延描画が到達しないようにする。

GPU方式が成立しない場合、黙って毎フレームのCPU読戻しへ切り替えない。原因・代替方式・負荷を報告して現在の作業を停止する。旧動作と結果は残す。

完了確認: テストパターンの本番/モニター対応、黒/保持、モニター更新間引きと本番欠落のカウンター分離、モニター有無の短時間性能比較を保存する。GPU読戻しは試験時のみに使用してよい。

### Step 4 — 1領域へのモード切替

- 停止中のキュー選択/行再生をPreviewPlayerへ接続する。
- 配信開始時はPreviewPlayer停止と音声解放を待ってから、領域をProgramへ貸し出す。準備中は黒を表示する。
- 配信中は本番映像と本番観測を表示する。選択行変更やキュー再生要求は無効化・拒否する。
- 停止完了後、Program側リソースと保留フレームを解放し、Cueへ戻す。選択キューの先頭を表示するだけで音声/再生を自動開始しない。
- 本番モニター単独障害と、本番送出自体の障害を分けて通知する。

完了確認: Cue再生→配信準備→本番→停止確認取消→停止承認→Cue先頭表示の一連の流れを確認する。

### Step 5 — 配信ボタンと確認ダイアログ

- Arm/Disarmを実装内部の概念として残す場合も、表示は「配信」「配信停止」に統一する。
- RequestStopAsync等の共通入口を作り、ボタン・Esc・本番出力WM_CLOSEから利用する。
- ネイティブのEsc/WM_CLOSEで即時に出力を破棄しない。要求をUIへ通知し、確認の承認後に実際のキャンセル/破棄を実行する。
- Avaloniaの非同期ShowDialogを用い、UIスレッドを同期Wait/Resultでブロックしない。モーダル中も描画ディスパッチとLTC更新が動くことを試験する。
- ダイアログ多重表示を防ぐ。取消でClock/デコーダー/出力を再作成しない。
- 終了確認は「停止して終了」の単一承認へ集約する。途中で取消された場合はclosingフラグを解除する。
- 描画エラー等のシステム停止はこの確認入口を経由させず、障害終了処理を使う。

### Step 6 — 設定モーダル

- SettingsDialogと編集用SettingsDraftを用意し、既存設定項目を移す。
- 適用前にデバイス/画面選択と数値範囲を検証する。キャンセルでは保存・受信再構成をしない。
- 配信状態を開く時だけでなく適用直前にも確認する。配信中は閲覧専用。
- 設定適用後の受信再構成と永続化の順序を決め、失敗時にUI表示と実動作が食い違わないようにする。
- 入力再構成中に配信開始できないようにする。設定モーダルを閉じること自体でプレビューを再開しない。
- 試験では--settings等の分離先を使用し、ユーザーのUR22C/L/29.97 DF設定を試験値で上書きしない。

### Step 7 — 行操作・シーク・レイアウト

- キュー行に再生/一時停止/再開と停止を配置する。再生対象はCueIDと完全なファイルパスで識別し、同名ファイルを混同しない。
- 行再生は対象選択→ロード→再生を共通サービス経由で実行する。他のプレビューの後着ロードを無効化する。
- 映像側の重複した再生ボタンを撤去する。シーク/音量/ミュートは停止モードだけ表示する。
- シーク追従の抑止条件を「ポインター/キーボードで位置指定中」に限定する。IsPointerOverや単なるフォーカスを条件にしない。
- ポインター捕捉喪失、キュー変更、モード切替で操作状態を確実に解除する。
- 指定タイトル文字を削除し、TC/受信状態/配信/設定を上部へ配置する。現在のドラッグ並べ替え後の再バインドとTC欄幅の修正は維持する。

## 4. 検証計画

| ID | 試験 | 合格条件 |
|---|---|---|
| U01 | ホバー/フォーカス中の再生 | つまみと時刻が進む。指定操作中のみ追従を止める |
| U02 | マウス/キーボードシーク、捕捉喪失 | 確定位置へ移動し、解除後追従。遅延シークが本番へ届かない |
| U03 | 停止中LTC、5モード、喪失/復帰 | 表示・状態更新。未受信/保持/実受信を区別 |
| U04 | 配信開始/停止を反復 | 入力を二重openしない。配信停止後もLTCが進む |
| U05 | 配信停止確認の承認/取消 | 確認中も送出継続。取消は状態維持、承認だけ停止 |
| U06 | Esc、出力WM_CLOSE、アプリ終了 | 確認を迂回せず、多重確認なし。取消で動作継続 |
| U07 | 設定の適用/取消/不正値 | 保存と受信再構成が一致。取消で変更なし |
| U08 | 配信中の設定閲覧 | 変更不可。送出/TC/モニターは継続 |
| U09 | 行操作、同名別パス、別キュー停止 | 正しいキューだけ操作。配信中はサービスでも拒否 |
| U10 | 単一領域の所有権切替 | 二重描画/音声残留/古い通知なし。停止後は先頭、無音 |
| U11 | 本番モニターの黒/保持/切替/ジャンプ | 本番の採用済み映像に対応。別スケジューラーなし |
| U12 | モニター有無の負荷比較 | 本番/モニターの提示・間引きを分け、時間/欠落/使用量を記録 |
| U13 | 開始失敗、準備中取消、終了競合 | 遅延して送出開始しない。リソースを解放 |
| U14 | モニター障害/本番障害 | 単独障害を識別。本番への不要な停止確認待ちなし |

自動試験では模擬入力の寿命/呼出回数、確認結果の注入、表示所有権の世代番号を検証する。ネイティブWM_CLOSE/Escと実モーダル、ホバー、行操作、ファイルダイアログは実画面でも確認する。

合成LTCによる統合試験と、UR22Cへ実LTCを入力する試験を別記する。実入力を利用できない場合は未実施と明記し、合成入力のPASSで置き換えない。

モニターあり/なしの比較は同一素材・同一設定で行い、Present成功、提示間隔、読み飛ばし/繰返し、モニター更新数、CPU/メモリ等を保存する。物理同期精度・2時間運転の合格基準はPhase 6に残し、この短時間比較で保証しない。性能結果に未解決の悪化がある場合は完了扱いにしない。

### 回帰試験

- Phase 1〜4の34試験を継続する。特にLTC変換、喪失/復帰/ジャンプ、後発優先、表示順独立、HAP GPU色変換、混在送出を維持する。
- Phase 5の音声・一時停止・シーク・音量・停止・ARM排他試験を維持する。入力寿命/画面モードの変更に必要な期待値だけ変更し、判定を緩めない。
- 新しい受入試験と既存回帰の結果を別ファイルで保存する。
- モニターは間引くため、全画素の同時刻一致を要求しない。送出フレームID/PTSに対応する縮小画像を検証する。読戻しによる検証負荷は通常再生の性能測定から分ける。
