# LTC同期メディアプレイヤー 開発指示書

## 1. 開発目的

Windows 11向けのLTC同期メディアプレイヤーを開発する。

本アプリケーションは、外部LTCタイムコードを基準として、複数の動画ファイルを指定時刻に再生し、選択したディスプレイへフレーム単位で同期した映像を送出することを目的とする。

**要件定義書 v0.4を正式な仕様とする。**

ただし、F02については以下の詳細仕様を追加する。

- Windowsの音声入力デバイスを列挙・選択する
- ステレオ入力のL/Rチャンネルを選択できる
- 入力レベルとLTC受信状態を表示する
- デバイス切断・再接続を検出する
- デバイスとチャンネルの選択を保存する
- USBオーディオインターフェースに対応する

## 2. 開発の基本原則

### 2.1 段階的な実装

開発を独立したフェーズに分割する。

**一度の作業で全機能を実装しようとしないこと。**

各フェーズでは以下の順序を守る。

1. 既存コードと要件を確認する
2. 実装対象と影響範囲を特定する
3. 必要なコードだけを変更する
4. ビルド・テストを実行する
5. 結果を報告する
6. 次フェーズに進まず停止する

ユーザーの明示的な指示があるまで、次のフェーズへ進まないこと。

### 2.2 利用上限と作業量の管理

- 不必要なファイルの全件読み込みを避ける
- 調査対象を現在のフェーズに限定する
- 動作する既存コードを理由なく書き直さない
- 大規模なリファクタリングを勝手に行わない
- 同じテストを無意味に繰り返さない
- 問題が発生した場合は原因を絞って修正する
- 外部ライブラリの導入は必要性とライセンスを確認する

フェーズ終了時には、変更ファイル、実装内容、テスト結果、未解決課題を簡潔に報告する。

## 3. 技術スタック

原則として以下を採用する。

| 領域 | 技術 |
|---|---|
| 開発環境 | Windows 11 / Visual Studio |
| 言語 | C# / .NET |
| GUI | WPF |
| LTC入力 | WASAPI / NAudio |
| LTCデコード | libltc |
| 動画デコード | FFmpeg |
| HAP対応 | FFmpeg / HAP関連ライブラリ |
| 描画 | Direct3D 11 |
| 出力管理 | DXGI |
| 設定保存 | JSON |

採用予定のライブラリで要件を満たせない場合は、代替案と影響を報告してから設計を変更する。

## 4. アーキテクチャ原則

以下の責務を分離する。

- **AudioInputService**：LTC音声入力とデバイス管理
- **LtcDecoder**：LTCデコード
- **MasterClock**：外部タイムコードに基づく時刻管理
- **CueScheduler**：現在時刻に対応するキューの選択
- **MediaDecoder**：H.264 / HAP / HAP Qのデコード
- **FrameBuffer**：デコード済みフレーム管理
- **FrameScheduler**：描画対象フレームの選択
- **VideoRenderer**：Direct3D 11による映像描画
- **PreviewPlayer**：独立したテスト再生
- **ShowProgramService**：キュー編集・保存・読み込み

UIのコードにデコードや同期制御を直接実装しないこと。

## 5. 開発フェーズ

### Phase 0 — 技術検証・開発環境構築

**目的：技術的な成立性を確認する。**

作業内容：

- .NET / WPFプロジェクトの作成
- FFmpegとの連携方式の検証
- Direct3D 11描画方式の確認
- HAP/HAP Qのデコード経路の調査と最小実装
- libltcの利用方法の確認
- 各ライブラリのライセンス確認

完了条件：

- プロジェクトが正常にビルドできる
- テスト映像をデコードできる
- HAP/HAP Qのデコード方式を確認できる
- LTCデコードの最小テストが可能である

**Phase 0では製品UIを作り込まないこと。**

### Phase 1 — 映像再生基盤

実装対象：

- MP4/H.264読み込み
- 映像デコード
- Direct3D 11描画
- 出力ディスプレイ選択
- フルスクリーン映像送出
- 基本的なエラーハンドリング

完了条件：

- 指定ディスプレイに1080p動画を表示できる
- UIと映像出力を分離できる
- ファイル読み込み失敗を検出できる

### Phase 2 — LTC同期

実装対象：

- Audio Inputデバイス選択
- 入力チャンネル選択
- LTCデコード
- MasterClock
- フレーム単位の再生位置計算
- 同期オフセット
- 同期状態表示

完了条件：

- LTCの時刻を取得できる
- LTC時刻に対応する動画フレームを選択できる
- 累積的な再生位置ドリフトを防止できる

LTC受信と実際のディスプレイ表示タイミングは分けて計測すること。

### Phase 3 — 上演プログラム

実装対象：

- 動画のD&D登録
- 開始TCの個別入力
- キュー追加・削除・複製
- D&Dによる表示順変更
- 有効・無効切り替え
- JSON保存・読み込み
- 後発優先の自動切り替え
- 再生区間の重複警告
- 次キューのプリロード

重要な仕様：

- キュー表示順は再生順に影響しない
- 再生順は開始TCによって決定する
- 後発キューの開始時刻で前の映像を打ち切る
- 重複区間は許可し、小さな警告を表示する
- 同一開始TCの有効キューは競合エラーとする
- プリロードも開始TC順で決定する
- 動画のない区間は黒画面とする

完了条件：

- 複数動画の上演プログラムを作成できる
- LTCに従って映像が切り替わる
- LTCジャンプ後も正しい映像を選択できる

### Phase 4 — HAP対応

実装対象：

- HAP MOV再生
- HAP Q MOV再生
- GPUテクスチャ転送
- HAP Qの色変換
- HAP動画のプリロード
- HAPとH.264が混在するキューの切り替え

完了条件：

- HAP/HAP Qが正常に表示される
- コーデックの異なるキューを切り替えられる
- デコード・描画の性能を計測できる

Phase 0で確認した技術方式を利用し、既存の再生基盤を不必要に作り直さないこと。

### Phase 5 — 個別プレビュー

実装対象：

- 選択キューのテスト再生
- 再生・一時停止・停止
- シーク
- プレビュー音量調整
- AAC / PCM音声再生
- 本番出力とプレビューの状態分離

完了条件：

- LTCなしで動画をテスト再生できる
- 動画内音声をプレビューできる
- プレビュー操作が本番出力に影響しない
- ARM中のプレビュー再生を禁止できる

本番LTC同期音声出力は実装しないこと。

### Phase 6 — 安定化・実機検証

検証対象：

- 長時間連続再生
- フレーム欠落・重複
- デコード遅延
- LTC入力喪失・復帰
- LTCの時刻ジャンプ
- キュー切り替え
- HAP高負荷再生
- 入力・出力デバイスの切断
- 出力遅延・同期精度

完了条件：

- 2時間以上の連続動作試験を通過する
- 同期誤差とフレーム欠落を記録できる
- 異常発生時に予測可能な動作をする
- 残存する制約と未達要件が明確になっている

## 6. テスト方針

単体テスト可能な処理は、実機依存部分から分離する。

特に以下を自動テスト対象とする。

- LTC時刻とフレーム番号の変換
- 29.97 DF/NDFの処理
- キュー選択ロジック
- 後発優先の動作
- 重複区間の検出
- 同一開始TCの競合検出
- 表示順を変更しても再生結果が変化しないこと
- LTCジャンプ時の再生位置計算
- JSON保存・読み込み

実機でしか確認できない映像出力精度については、測定方法と測定結果を別途記録する。

## 7. 作業報告形式

各フェーズの終了時には以下の形式で報告する。

**実装フェーズ：** Phase X

**実装した機能：**
実際に完成した機能を記載する。

**変更したファイル：**
新規作成・変更した主要ファイルを記載する。

**検証結果：**
ビルド、単体テスト、実機試験の結果を記載する。

**未解決事項：**
不具合、性能上の懸念、未実装の機能を記載する。

**次フェーズへの影響：**
次の工程に影響する技術的な問題のみ記載する。

未実施のテストを成功したと報告しないこと。

## 8. 作業停止ルール

以下の場合は、無理に実装を進めず現在のフェーズを停止する。

- 予定した技術方式が成立しない
- 重大なライブラリ互換性問題が発生した
- アーキテクチャの大幅変更が必要になった
- 現在のフェーズ外の大規模実装が必要になった
- 同じ不具合の修正を繰り返しても改善しない

停止時には、原因、実施済みの対策、残る選択肢を報告する。

## 9. 初回実行指示

最初の作業では**Phase 0のみ実施**すること。

Phase 0では、HAP/HAP Q、FFmpeg、Direct3D 11、libltcの技術的な成立性を優先して検証する。

実行環境にWindowsのGPU・音声入出力機器がない場合は、検証可能な部分だけを実施し、実機検証が必要な項目を明確に分離する。

Phase 0の終了後、結果を報告して停止する。ユーザーの指示なくPhase 1へ進まないこと。
