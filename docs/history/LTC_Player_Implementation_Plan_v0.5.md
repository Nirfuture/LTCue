## 1. 方針

再生仕様→最小技術検証→共通エンジン→表示先分離→UI確定→総合検証の順に進める。各段階で設計・実装・試験・結果レビューを行い、成立を確認してから次段階へ進む。全面改修を許容するが、実績のある同期・復号・シェーダーを理由なく再実装しない。

今回は計画と要件の提出まで。以下の実装・試験は未着手である。

## 3. 目標となる責務分離

- PlaybackCore: 時計、キュー選択、再生モード、手動操作、セッション世代。Avaloniaやコマンドライン引数へ依存させない。
- DecodeSession: 現在・次キュー・復旧の寿命、キャンセル、解析キャッシュ、最大2ストリーム。
- RenderSession: 共通D3Dデバイス、キャンバス、HAP／BGRA描画、蓋画合成、フレームID。外部出力がなくても存在する。
- PreviewSink: 共通GPU画像の縮小、最新1枚、更新間引き、リサイズ・遮蔽復帰。
- ExternalOutputSink: ディスプレイHWND、Flip/BitBlt、開始・提示・解除。復号や再生時計を所有しない。
- PlaybackCoordinator: 上記のコマンド直列化と状態遷移。キャンセル要求は長い準備処理の後ろへ積まない。
- SettingsRepository / DiagnosticsWriter: 設定トランザクションと有界非同期ログ。
- UI: コマンドと不変スナップショットを扱う。同期計算・復号・ネイティブ資源寿命を埋め込まない。

クラス名は仮称。不要な抽象化や全面MVVM化を先行させない。ネイティブ資源の解放は所有スレッド上で行い、単純なfinalizer任せにしない。

## 4. 実施段階と判定

### 段階0: 仕様と基準状態の固定

作業:
- 対象コミット、未コミット差分、SDK、依存、素材、設定分離先、GPU・ディスプレイ条件を記録する。
- v0.5の操作状態表を確定。特に停止・終端の保持、出力中操作制限、音声停止後の時計連続性、1/4の解釈を明記する。
- 現行の既知失敗と未実施を一覧化し、検証対象から黙って外さない。
- 変更前バイナリと結果を保存する。利用中アプリと試験用インスタンスを分ける。

判定: 合意した再生仕様と、変更する／維持する挙動を一覧で説明できること。

### 段階1: 現象の再現と性能基準

作業:
- 動画選択、再生開始、一時停止再開、シーク、連続選択、出力オン・オフで画面を記録する。
- プレビュー矩形、HWND世代、Black、ロード状態、Present、再構成の時刻を関連付ける。
- 進捗表示の有無だけを変える試験でレイアウト変動との因果を確認する。表示を消しても残るちらつきは別原因として調べる。
- 同一素材でCPU、GPU、メモリ、初期準備、提示間隔、LTC遅延、復旧時間、プロセス数を測る。
- 100／500／1000キューの一括読込・検証と、ログ遅延を測る。

判定: ちらつき原因の根拠、比較可能な性能基準、次段階の数値判定を記録する。原因未確定なら未確定としたまま仮説を管理する。

### 段階2: 共通GPU映像と2表示先の最小検証

作業:
- 実プレイヤーを全面変更する前に、外部HWNDを持たないD3Dデバイス・合成先を作る。
- 同じ合成済みGPU画像をプレビューと任意の外部swap chainへ提示する。
- 外部表示先を繰り返し追加・削除し、デバイス・合成元・フレームIDが維持されることを確認する。
- 縮小、縦横比、黒帯、蓋画両端・中間・反転・非累積、保持画像の再描画を画素比較する。
- プレビュー遅延、リサイズ、遮蔽、外部作成失敗を注入する。
- 初期実装は既存UIスレッドの描画境界を活用。専用スレッド化が必要かは測定で決める。

判定: A01〜03、A07の最小成立。通常経路でCPU読戻しなし。Flip/BitBlt両方を小さい出力ウィンドウで確認する。

成立しない場合: 毎フレームCPU読戻しや二重復号へ黙って切り替えず、原因・代案・負荷を報告して設計を見直す。

### 段階3: 共通再生エンジンと操作モデル

作業:
- ProgramPlaybackのキュー・フレーム選択、復旧をDecodeSessionと共通エンジンへ移す。
- WAITING／LOST時の手動再生・停止・シーク・一時停止を同じエンジンへ統合する。
- 確認用音声を独立した出力先とし、音声有無で映像時計が巻き戻らないようにする。
- ロード要求のキャンセルと世代検査を導入し、準備完了後にだけフレームを採用する。
- 共通スナップショットを発行し、再生の実状態とUI表示の根拠を統一する。

判定: 既存同期7条件に加え、連続選択、LTCによる手動割込み、音声停止時の位置連続性、停止・終端、シーク、復号エラーの試験が通る。最大2復号・上限付きバッファを維持する。

### 段階4: 外部出力ボタンと資源寿命の置換

作業:
- Arm/Disarmを外部表示先のAttach/Detachへ置き換える。
- 再生処理停止、位置引継ぎ、プレビューHWND再作成を出力オン・オフ経路から除去する。
- 停止確認、取消、開始失敗、終了、二重操作を直列化する。
- 解放失敗でも状態解除と残りの解放を実行する。プレビュー復旧エラーで出力中フラグを残さない。
- 外部出力停止時に確認音声を自動再開しない。

判定: A01、A03、A06、A09を通過。繰返しオン・オフでセッション・位置・フェードが維持され、外部HWND／swap chainだけが増減する。

### 段階5: 設定・ログ・キュー編集とプロジェクト境界

作業:
- 設定の検証・保存・実動作への適用を統合し、途中保存と不完全な巻戻しを解消する。
- 画像欠損を黒へ統一し、無関係な設定変更を妨げない。
- 有界非同期ログと一括キュー更新を導入する。
- 動作を維持した単位でCoreプロジェクトを作り、ソースリンクと同名テストスタブを実装インターフェースへ置き換える。
- 旧PreviewPlayer／SynchronizedPlaybackなどの利用箇所を確認し、機能移管後に削除または検証用へ隔離する。
- ネイティブ共通宣言と実装を分け、資源の途中初期化を成功後の一括採用にする。

判定: 保存障害・破損設定・欠損画像・大量キュー・低速ログの試験を通過。既存JSONと設定を読み込める。不要な旧経路が製品に残っていないことを確認する。

### 段階6: UI仕様の確定と実装

先行条件: 再生状態と表示先の契約が成立し、出力オン・オフの基本試験が通過していること。

作業:
- 映像→シークバー→時刻・素材名→音声→蓋画の順を基本に、通常／狭幅／縦長の画面案を用意する。
- 進捗領域を固定し、短時間の表示抑制と最低表示時間を実画面で調整する。
- 映像準備中の旧フレーム保持と、真の黒区間を視覚的に区別する。
- フェード秒数の直接入力、プリセット、0秒の即時表示を比較して確定する。進行中の秒数変更は次回適用にする。
- 読取専用の進行表示と操作可能なシークを区別する。
- フォーカス、キーボード、ポインター捕捉喪失、タブ順、100〜200% DPIを確認する。

判定: A10〜11。進捗の表示切替で映像矩形とHWND世代が変わらない。操作を録画して目視のちらつきも確認する。UI案は実装前に比較・レビューできる形で提示する。

### 段階7: 総合回帰と性能判定

作業:
- 同期・キュー・手動再生・蓋画・表示方式・出力操作・設定・レスポンシブの回帰を実行する。
- 1080p H.264／HAP／HAP Q、縦横キャンバス、出力なし／あり、プレビュー有無を同一条件で比較する。
- 外部出力切替100回、連続選択・シーク、モーダル、ログ／設定障害、終了競合を確認する。
- GPU提示、映像遅延、CPU、GPU、メモリ、ハンドル・プロセスの残留を確認する。
- 一時的なデバッグ用画素読戻しは性能測定から除外する。

判定: A01〜12の証拠を保存。段階1からの悪化は原因と許容理由を示す。測定なしに「軽くなった」「完全一致」と結論づけない。

### 段階8: 実機耐久・配布

作業:
- 対象環境を決め、実LTC、他の環境／GPU、2時間以上の連続運転を行う。
- 物理同期精度が必要な運用では、内部PTSとは別に測定方法・許容誤差を定める。
- 標準Flip全画面停止の報告条件は、利用者と実施条件を確認して独立した診断にする。
- CURRENT仕様、QUICKSTART、TROUBLESHOOTING、BUILD、検証記録とリリースノートを更新する。
- コミットから新バージョンをパッケージ化し、ソース・ハッシュ・署名状態・ライセンスを照合する。

判定: 実施／未実施を明記して配布判断する。GitHubへの公開は別の指示に従う。既存リリースを上書きしない。

## 5. 試験資産と追加する検証

| 区分 | 継続・追加する内容 |
|---|---|
| 純粋ロジック | DF/NDF、後発優先、表示順独立、競合、世代、復旧7条件 |
| 新設計の契約 | セッションID維持、フレームID対応、出力Attach/Detach、最新要求だけ採用 |
| 音声 | 一時停止・再開・ミュート、出力開始時停止、映像時計の連続性、音声資源解放 |
| GPU | HAP/Q色、黒帯、蓋画合成、縮小基準画像、両表示方式、遮蔽復帰 |
| 障害 | HWND／swap chain作成失敗、描画失敗、デバイス喪失の分類、設定保存拒否、低速ログ |
| UI | 進捗表示と矩形不変、直下シーク、連続選択、秒数入力、DPI・縦長・最小サイズ |
| 運用 | 設定互換、JSON、単一起動、出力確認・取消・終了、配布物照合 |

既存結果は出発点として利用するが、表示経路を変更した部分のGPU・UI試験は再実行する。旧単体エンジンPTS整合試験の保留は、対象経路の移管後に扱いを説明する。

## 6. 各段階の成果物と変更管理

各段階で次を提出する。

1. 仕様差分と設計判断。
2. 変更した責務・主要ファイル。
3. 試験条件、結果、性能比較、再現手順。
4. 未解決事項と次段階への影響。
5. 対象コミット・設定・素材・ビルドの識別情報。

一つの段階を独立してレビュー・復元できる単位にする。成立しない方式、未解決の性能悪化、大きな仕様変更が出た場合は設計へ戻り、後段のUI実装で隠さない。ユーザー設定・上演データは試験で上書きしない。

最初の着手対象は段階0〜1。その後、段階2のGPU技術検証を通してから共通再生系を本実装する。
