# 同期遅延の検出と復旧

## 対象

本番のキュー再生（ProgramPlayback）で、LTCに対して復号済みの映像が遅れた場合の処理です。

入力LTCの受信状態と、映像の追従状態は別に扱います。入力がLOCKEDでも映像が遅れる場合があるため、表示するフレームのPTSと、そのキューに対するLTCの経過時間を比較します。

## 動作

- 遅れが200msまたは動画の3フレーム分の大きい方を超えると、遅延秒数を画面に表示します。
- 現在の復号を維持しながら、LTCの現在位置より少し先を別の復号処理で準備します。
- 準備ができたフレームは、そのタイムコードに達してから採用します。
- 復号が遅い間に同じ準備処理を何度も破棄し直すことはしません。復旧の試行開始は最短でも1秒間隔です。
- 先読みする時間は、観測した初期準備時間を基に250ms～2秒の範囲で決めます。
- 復旧中は次キューの先読み用リソースを使い、現在の復号と合わせて同時に2つまでに抑えます。
- LTC入力が失われた場合は従来どおり最後の映像を保持します。入力復帰やジャンプで世代が変わった場合は、古い復旧処理も破棄します。
- 復号そのものが失敗した場合は、従来の本番エラー通知・停止処理に伝えます。

物理ディスプレイ上の同期精度を保証するものではありません。処理能力が不足する場合はフレームの読み飛ばしや映像の保持が発生し、すべてのフレームを等速で表示することはできません。

## 診断情報

ProgramObservationに次の項目を追加しています。

| 項目 | 内容 |
|---|---|
| LagSeconds | その時点で選んだ映像フレームの遅れ。入力喪失中や対象映像がない場合はnull |
| Recovering | 再同期用の復号を準備しているか |
| RecoveryAttempts | この配信で再同期の準備を開始した回数 |
| InputGeneration | LTCのジャンプ・復帰を識別する時計の世代 |

## 検証

`dotnet run --project tests/SyncRecovery/SyncRecovery.csproj -c Release`

実際の時計・キュースケジューラー・フレームバッファを使い、復号と描画だけを代替した回帰試験です。連続入力、低速復号、遅い準備、負荷からの回復、前後へのジャンプ、入力喪失と復帰、復号エラーを検証します。

実動画・GPUの試験は、検証用ビルドの `--verify-sync-recovery-output` で行います。30秒のHAP素材を使い、連続入力・入力喪失時の保持・入力復帰・前後へのジャンプからの復旧を確認します。通常の `scripts/test.ps1` に両方を組み込んでいます。

従来の初期テストにあったフレーム番号の半秒ごとの巻き戻しは、連続入力の試験から取り除きました。ジャンプは独立した障害条件として検証します。
