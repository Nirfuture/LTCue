# 蓋絵連続フェードの性能低下：分析と対処方針

対象：`fix/output-presentation` / `d3fd93a`。2026-11-19のソース調査と保存済み診断結果の再分析。今回、新しい性能測定・実LTC試験・製品コード変更は行っていない。

## 結論

最有力の原因は、動画更新と蓋絵タイマーが別々に合成・外部提示を実行し、同じUIスレッドで垂直同期待ちを繰り返すこと。GPU合成そのものの能力不足と断定する根拠はない。提示経路の重複はコードで確認できるが、待ち時間の内訳と改善効果は追加計測が必要。

## 根拠

- `MainWindow.Presentation.cs`：16ms周期の`coverTimer`が`Surface.RefreshCover()`を実行。
- `PreviewHost.RefreshCover()`：フェード量が変化するたびに`Canvas.Redraw()`を実行。
- `PreviewHost.Present()`：動画フレームにも最新フェード量を適用して`Canvas.Present()`を実行。
- `RenderSession`：両経路はそれぞれネイティブ合成とプレビュー更新へ進む。
- `native/phase5/Composite.inc`：`PresentComposite()`は合成に続き`swap->Present(o->embedded?0:1,0)`を実行。外部出力では同期間隔1の提示となる。
- `ProgramPlayback`の新規フレームなしの経路にも`presentation.Refresh()`があり、更新源はタイマーだけではない。

保存済み`artifacts/ltc-test-assets/evidence/cover-toggle-{hap,mp4}/results.json`のduring区間：

| HAP・1秒フェード反転 | 6.436 | 27.81 | 386 | 386 | 0 | 205 |
| MP4・切替なし | 6.399 | 60.01 | 384 | 384 | 0 | 0 |

フェード中も合成・外部提示の呼出頻度は約60回/秒を維持する一方、異なる動画フレームは約半分。動画以外の再合成が提示枠を消費する仮説と整合する。これは呼出数であり、物理ディスプレイの表示回数の測定ではない。再試行増加は観測されていない。CPU集計だけではGPU待ちの有無を判定できない。

## 推奨する修正方針

1. 最新コミットから`codex/fix-cover-fade-pacing`を作成し、最新製品経路に診断を追加する。既存の`Run-Diagnostic.ps1`は保存スナップショットをビルドするため、そのままでは最新コードの検証にならない。
2. 動画提示・タイマー更新・保持更新を識別して、回数、合成時間、外部Present時間、UIへの投入から実行までの時間を集計する。まず現状の再現と待ち時間の集中箇所を確認する。
3. 動画と蓋絵の変更を一つの描画周期にまとめる。動画が届く周期は、そのフレームに最新フェード量を適用して一度だけ合成・提示する。蓋絵更新は変更要求として集約し、独立した同期提示を重ねない。
4. 動画が来ない周期でも、停止・入力待ち・デコード遅延・低fps素材のフェードは進める。単に「再生中はタイマーを止める」方式にはせず、動画到着と蓋絵更新を調停する。切断検出・停止要求・遮蔽復帰・未完了提示の再試行は引き続き処理する。
5. それでも不足し、描画処理の設計見直しが必要と判明した場合は、下記の停止条件に従う。毎回のShaderResourceView生成の削減は副次的最適化として扱う。

## 作業範囲と停止条件（2026-11-19 ユーザー指示）

- 現行の共通キャンバス・合成・プレビュー・外部出力の構成を維持し、更新要求の集約と描画タイミングの局所的な調停を前提に進める。
- 描画処理の設計を見直す必要が生じた場合は、その時点で作業を一旦停止する。設計変更の実装へ自動的に進まない。
- 例えば、描画・提示をUIスレッドから別スレッドへ移す、合成と外部提示を構造的に分離する、提示方式を非同期化する、キャンバスや描画資源の所有関係を変更する必要がある場合は、この停止条件に該当する。
- 停止時は、判明した原因と計測結果、局所修正では不足する理由、必要な設計変更の範囲・影響・代案をまとめてユーザーへ報告し、方針の確認を得てから再開する。途中の変更と診断結果は保存し、未検証の変更を解決済みとして扱わない。
- この停止条件は、上記の修正方針・検証計画より優先する。

## 検証計画

- 合成時計：同じディスプレイ2・1920×1080・標準・全画面・音声あり・60fps MP4/HAPで、切替なし／0秒／1秒フェードを比較。0.8秒ごと8回の反転と回復区間を維持し、順序を反転して複数回測定。
- 主判定：フェード中も動画提示が切替なしの約60fpsに近づくこと（暫定目標58〜60fps）。スキップが継続的に約30枚/秒増加する現象が消えること。平均だけでなく短区間の提示間隔と停止も確認する。
- 機能回帰：停止・入力途絶中のフェード完了、24/25/29.97/30fps素材、反転時の連続性、終端値0/1、実サイズ蓋絵、外部出力OFF、標準/互換、非表示復帰、切断検出、プレビューとの一致。
- 実LTC：合成時計での改善後、iPhone→UR22Cの入力で目視・聴感を伴う再確認を別記録にする。音声状態Playingだけで同期合格にはしない。
- 全尺再生と2時間耐久は、その後の独立した受入項目として残す。
