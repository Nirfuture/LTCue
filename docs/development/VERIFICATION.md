# 一括検証

`cue-selection-scroll`の試験は、低いウィンドウでの1行/4行のクリックと再クリック、手動スクロール位置、TC編集、チェックボックス、Ctrl/Shift選択、一覧内キー移動、縦積み下端への到達、画面外へのフォーカス追従を検証する。`measurements.json`へ外側Offset・DataGridのスクロールバー値・フォーカス・選択ID・操作ボタン/列ヘッダー座標を記録し、前後のPNGも保存する。詳細は[修正記録](../history/records/2026-11-20_003_CUE_SELECTION_SCROLL_FIX.md)を参照。

MP4初回手動再生の単一復号は `mp4-single-start` の試験で検査する。先頭の提示回数、後続フレームのハッシュ/PTS、段階別取消、採用拒否、権限・素材版・寸法変更、満杯キューの終了、停止再開、単独Load、破損時の解放を対象にする。結果と前後比較は [MP4単一復号の記録](../history/records/2026-11-20_001_MP4_SINGLE_DECODE_START.md) を参照。

最終候補の自動検証には`./scripts/test.ps1`を使用する。古い個別スクリプトで一部を通した結果を、全体の合格とは扱わない。

## 実行条件

- Windows x64、D3D11対応GPU、接続済みディスプレイ、WASAPIの音声出力先。
- PowerShell 7.2以降。リポジトリのglobal.jsonに対応した.NET SDK、Visual StudioのMSVC x64とWindows SDK。
- FFmpeg/ffprobeをPATHへ配置。libx264、AAC、HAP、PCM、libmp3lameのエンコーダーが必要。
- 実行中の製品版を終了する必要はない。他の検証版が動いている場合は開始せず通知する。

通常のビルドと実行：

```powershell
./scripts/test.ps1
```

別のdotnetを使う場合：

```powershell
./scripts/test.ps1 -DotnetPath C:/path/to/dotnet.exe
```

検証版は新規の結果フォルダー内へランタイム同梱で発行する。通常の製品版・検証版の既存フォルダーを上書きしない。結果フォルダーが既にある場合も停止する。

既にビルドした候補を再検証する場合：

```powershell
./scripts/test.ps1 -SkipBuild `
  -DotnetPath C:/path/to/dotnet.exe `
  -ExecutablePath C:/path/to/verification/LTCue.exe `
  -SyncRecoveryAssemblyPath C:/path/to/SyncRecovery.dll `
  -HapPreparationAssemblyPath C:/path/to/HapPreparation.dll `
  -JumpRecoveryAssemblyPath C:/path/to/JumpRecovery.dll `
  -TimecodeEditingAssemblyPath C:/path/to/TimecodeEditing.dll `
  -ResultPath C:/path/to/new-results
```

`-SkipBuild`でも専用の検証版が必要。ランタイムを同梱しないビルドや通常版は、起動前の検査で拒否する。計算系4プロジェクト（SyncRecovery、HapPreparation、JumpRecovery、TimecodeEditing）のDLLも事前にビルドしておく。

素材は既定で新規生成する。再利用する場合は`-FixturesPath`と`-AudioFixturesPath`を両方指定する。必要な全ファイルを開始前に検査する。いずれの場合も使用した素材のハッシュを記録する。

LTC復帰とタイミング表示には、映像・音声付きの`h264-aac-sync-30s.mp4`を使用する。6秒素材を5回連結した30秒の素材を生成し、喪失・復帰と再準備の途中でキューが終了することを避ける。既存の素材フォルダーを再利用する場合も、このファイルが必要。

`timing-status`の初回同期と喪失後の復帰は、それぞれ最大15秒まで準備完了を待つ。他の表示待ちの上限6秒と、製品の遅延判定しきい値・継続時間は変更しない。各待機の実時間と終了時状態を`waits.json`へ保存し、長い準備時間を記録に残す。

各版で実際に実行した範囲・失敗・再試験は[確認記録](../releases)へ記載する。以下の対象一覧は、最新ソースで全件合格したことを示すものではない。

## 合格の条件

試験一覧は`scripts/verification-suites.json`に一元化し、検証版にも埋め込む。実行ファイル内の一覧がソース側と異なる場合は、古いビルドとして開始前に拒否する。通常版の判定にはPEメタデータを読み、判定のためにアプリを起動しない。

各試験は別プロセス・別設定・別証跡フォルダーで順番に実行する。画面提示を確認するため、検証版のウィンドウは前面に表示する。合格には終了コード0だけでなく、証跡の存在、形式、全項目の結果、予定件数が必要。空の結果や一部だけの実行を合格にしない。ディスプレイ数で項目数が変わる試験は、非空の結果と全画面の合否を確認する。

アプリ側の上限はカタログのTimeoutSeconds（通常120秒）、計算系4スイートは各90秒。期限超過時は、その試験のために起動したプロセスツリーだけを終了する。製品版や他のアプリを終了しない。アプリ側の試験は失敗しても後続を実行し、全体として失敗終了する。計算系は不合格結果を集計するが、証跡の欠落・読込失敗などの例外では全体を中断する。

結果フォルダー：

```text
manifest.json       使用バイナリ・素材のSHA-256、実行対象外の理由
summary.json        合否・件数・終了コード・実行時間・失敗理由
sync-calculation/   CPUの同期計算
各試験名/           独立設定、JSON、画像、stdout.log、stderr.log
runner-failure.txt  全体が失敗した場合の記録
```

アプリ側の自動対象はカタログのMode=Autoで管理する。加えてCPU同期計算・HAP索引・ジャンプ境界・開始TC編集の4スイートを実行する。件数にはリサイズ、性能測定、音声開始の測定ケースも含まれるため、すべてを独立した単体テスト数と解釈しない。接続ディスプレイ数によって合計件数は変わる。

## 主な検証経路

- preview-recovery：製品と同じ共通GPUキャンバスを使い、色、保持、プレビュー非表示からの復帰、LTC喪失・再開、出力停止時のセッション維持を確認。
- default-show：4キューの動作に加え、黒区間で出力を再開しても時計が戻らず、その後のLTCで次のキューへ進むことを確認。合成DF信号も禁止ラベルを生成しない。
- manual-output：古い保持状態を拾わず、今回の再生開始→終端→保持の順に確認。出力オン・オフだけで同じ映像を保持することも画素比較する。
- 時刻差素材：早い音声はステレオ・映像PTS維持で生成。非ゼロ時刻のAACは高精度のコンテナ時刻を指定し、丸め誤差を試験素材へ混ぜない。

低レベルの旧レンダラー試験は部品の回帰として残す。製品経路そのものの検証は共通キャンバス・再生統合・復帰試験で行う。

## 開始時間の限定計測

専用検証版の`--verify-startup-measure`は、手動再生の初回と停止後4回を計測する。一括試験とは別の診断入口で、開始待ち時間と開始後の内部同期誤差を分けて扱う。提示API・WASAPI Startの時刻を物理的な表示・出音時刻とは扱わない。条件と結果は[検証環境Aの記録](../history/records/2026-11-13_003_STARTUP_CHECK_ENV_A.md)を参照。

## 対象外と保守用検証

`live-startup`は外部の実LTC源が必要なため手動試験。`redesign-baseline`は再設計前の履歴で、現行製品の受入試験に含めない。どちらも理由をmanifestへ記録し、自動合格数には含めない。

実際の機器切断、実LTC入力、他の環境、2時間以上の耐久、物理ディスプレイと出音の遅延は別工程。小さい出力ウィンドウや失敗注入による検証を、それらの実測の代用にしない。

ランナーを変更した場合は、保守用の誤判定防止試験も行う。

```powershell
./scripts/test-verification-runner.ps1 `
  -ProductAssemblyPath C:/path/to/product/LTCue.dll `
  -ResultPath C:/path/to/new-runner-checks
```

完全な証跡の受入、空・不足・失敗・欠落・fatal記録の拒否、通常版の起動前拒否、既存結果フォルダーの拒否、専用子プロセスのタイムアウトを確認する。

## LTC設定の個別適用

同期開始と補正値変更後は、新セッション自身の映像観測・音声プレイヘッドと新しい音声状態を待つ。画面側に残る前セッションの観測を準備完了の根拠にしない。補正値変更時の比較値は`offset-transition.json`へ保存する。

## 同期中の進捗・fps表示

同期中もシークバーは提示フレームの位置へ追従し、操作は禁止する。映像状態には半角の括弧でfpsを添え、累計スキップ数のツールチップは表示しない。fpsは異なるフレームのアプリ提示回数を1秒ごとに採取し、直近約2秒の平均から算出する。物理ディスプレイの表示fpsではない。素材fpsの90%未満が2秒継続すると数値だけ赤くし、回復や入力待ち・セッション変更で判定を戻す。音声の表示と既存の遅延判定基準は変更しない。

fpsの試験では計測窓・履歴初期化、1秒の更新制限、90%境界と継続判定・回復・色分けを確認する。既存のLTC状態遷移試験にも、シークバー追従・保持・復帰、fps表示、累計ツールチップ撤去の確認を含む。

## 素材情報の共有

media-analysisの試験は4素材保持・正規化・同時要求・個別/全取消・失敗再試行・途中JSON・変更中解析・差替え・両キャッシュの無効化・LRU・終了処理・作成時刻・映像制約・開始時刻の分離・実素材アダプター共有・リスト再検査・UIスレッド分離・未完了上限・サイズ上限・HAP素材版・旧索引の採用拒否を確認する。

開始計測は各素材で初回＋停止後4回を実行し、--startup-switch onでは4素材を登録して1→2→3→4→1を各5回ずつ再生する。conditions.jsonへ登録時間を記録し、transitions.jsonのinfo_ffprobe_start/index_ffprobe_start/decode_ffmpeg_startを区別する。analysis_begin/complete/cache_hitで共通解析を追跡する。各試行のvideo_first_present、video_clock_start、video_playback_first_present、audio_start_completeは別指標として残す。通常ビルドでは計測呼出しを除外する。

## PCM直接読取と起動待ち

direct-pcmは直接読取・FFmpegフォールバック・破損拒否・素材版変更・取消・資源解放・音声OFFとデバイス失敗からの明示復旧を確認する。詳細な形式範囲は後述する。計算系4DLLも最終ソースからビルドして使用する。

起動計測ではaudio_first_pcm（復号）、audio_first_write（WASAPIへ最初に投入）、audio_start_complete（Start復帰）を区別する。audio_decode_pathでmov-pcm/ffmpeg、直接読取の準備時間とFFmpeg起動時間を記録する。各試行のメモリ/ハンドル/音声プロセスと停止後・破棄後の資源も保存する。物理的な出音、実LTC、実機の切断は自動検証と別である。

## 48kHz PCM形式の検証

`direct-pcm`では6形式の先頭/中間/末尾/端数シーク、24bit符号境界、float特殊値（有限比較とは別分類）、22秒、co64、64bit/サイズ0 moov、正常BE/signed32フォールバック、破損時刻表、追加形式の満杯取消を検査する。S16 stereoの既存誤差基準を維持し、新形式は2e-7以下。任意固定切替計測は--startup-materialsで改行区切り絶対パス一覧を指定できる。

## 同期復旧の検証

正式な受入確認は冒頭の一括ランナーを使用する。以下は計算処理だけを調べる個別入口であり、一括検証の代わりにはしない。リポジトリのルートで実行する。

```powershell
dotnet run --project tests/SyncRecovery/SyncRecovery.csproj -c Release
```

実際の時計・キュースケジューラー・フレームバッファを使い、復号と描画を代替して、連続入力、低速復号、遅い準備、負荷からの回復、ジャンプ、入力喪失・復帰、復号エラーを検査する。

実動画・GPUの試験は検証専用ビルドの `--verify-sync-recovery-output`。一括ランナーでは30秒のHAP素材を渡し、連続入力、入力喪失時の保持、復帰・前後ジャンプからの復旧を検査する。JumpRecoveryの計算系試験も一括ランナーに含まれ、提示待ち・旧処理終了待ち中の再ジャンプ、初回受信、入力エラー、準備時間、先読み素材版の相違を扱う。連続入力とジャンプは独立した条件として検査する。

LTC設定の検証入口は `--verify-ltc-settings`。入力切替は検証用入力で再現し、実機切断・ケーブル切替の合格を意味しない。実行環境、証跡形式、失敗時の扱いは本書冒頭の一括手順を基準とする。
